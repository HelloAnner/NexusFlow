二、需求来源与需要确认的约束
----------------------------
产品目标：本次用户要求“全部功能真实、前端无 fake、后端达到预期设计”。

rewrite-contract.txt 用于识别现有技术栈和历史缩减项；本次不能用历史缩减替代功能补齐。

仓库约束存在旧描述，本方案不修改任何 AGENTS.md：
1. AGENTS.md 写 Rust/backend/frontend；实际只有 apps/api、apps/web、cli。
   建议确认：在现有 Bun/Next 工程实施，不重建 Rust 工程。
2. AGENTS.md 指定 nexusflow.pen；实际视觉源是 design.pen、design-exports/*.png。
   建议确认：以现存 design.pen 为设计源。未确认前不开始前端设计变更。

   页面描述按项目约束保留 Markdown，本整体方案及验收记录用 txt。
3. 父级允许本地单测，子项目禁止独立本地构建/测试；采用更严格的子项目要求：
   本地只编辑、Git/worktree、从干净 main 运行 make deploy。
   make deploy 内部必要编译可执行；独立单测、类型检查、功能验收均在服务器。
   不手工拆开部署，不在本地启动环境，不修改其他系统。

业务规则建议，整体确认时一并确认：
- 普通项目成员默认查看和处理个人分工，不自动获得项目编辑/派发权。
- 普通派发完成协调后仍需相关人员确认，确认前不占正式排程，可显示预估占用。
- 超载或全天冲突不能靠“仅警告”发布；必须调整，或由有权人员限期强制并留原因。
- SA 默认负责系统管理；敏感业务访问、兜底审批须显式授权/原因/审计，不能静默代批。
- 默认企业时区 Asia/Shanghai、日标准工时8h，人员工时可调整；周末/节假日规则由配置决定。
- 智能工具不在本系统自研9套引擎：已有外部工具接真实入口、授权上下文及使用记录。
  不能把 url="#"、弹“已打开”、虚构次数算成功；可用工具地址在配置中明确。

有冲突或无法确定的业务口径先标为阻塞，不由 agent 随意补设计。
方案确认不授权删除现有数据、不授权改 AGENTS.md、不授权部署其他系统。

三、现状：共性根因
------------------
A=apps/api/src，W=apps/web，C=cli/src；下文 file:line 均对应上述基线。

1. 多页接口成功也显示演示数据。
   W/lib/data.ts:7-12 用 demo 作 initialData，catch 所有错误后返回 demo。
   后端列表实际是 {items:[...]}；projects/team/files/tools/inbox 页面却判断顶层数组。
   修正解包还不够：空结果、少量结果、缺字段继续由 demo 补人名、附件、统计。
   my-work/load 甚至丢弃查询结果，直接显示固定任务、矩阵与冲突。
   首页主查询没有 demo 回退，但跳转的下游页面和部分字段仍不真实。

2. 交互未贯通。
   派发表单未收集真实输入，请求缺必填字段；第二步提交失败被吞掉后仍跳转。
   许多上传、下载、审批、协调、新建、搜索、调整计划按钮无处理器。
   甘特只静态导出 demo 项目ID；真实UUID深链及刷新没有正确页面契约。
   未匹配 API GET 可能被静态兜底返回首页HTML，HTTP 200不能证明功能存在。

3. 后端不是空壳，但有旁路与闭环缺口。
   已有真实认证、CRUD、派发审批、负载、文件存储、任务验收、报表聚合、审计。
   通用JSONB PATCH、专用动作、角色判断没有统一约束，可能绕过状态机或编辑范围。
   任务确认/负载生效、审批结束/待办关闭、项目归档/下游锁定不一致。
   负载DTO缺ratio，首页可能把实际占用呈现为0%；静态分析发现并发重检风险。

4. 工程与验证。
   A/router.ts 约106KB，混合13领域；A/records.ts、permissions.ts 和 CLI均为共享修改点。
   现有测试多使用mock，不能证明真实PG/Redis/MinIO、事务和服务器业务通过。
   readyz及部分冲突GET有写入副作用；部署只健康检查，没有全域CLI验收或提交身份校验。

四、“没有 fake”与“真实功能”的交付定义
--------------------------------------
每个页面操作必须具有以下链路，并进入功能清单：

  页面/按钮
      |
      v
  真实表单/筛选 -> 受校验DTO -> 鉴权API -> 事务/对象存储
      ^                                      |
      |                                      v
  刷新后的真实状态 <- 服务端回读 <- 审计/版本/通知/负载联动
                                      ^
                                      |
                                  同等能力CLI

清单文件：docs/function-coverage.txt，实施第一步建立，之后每次交付更新。
每行：需求ID | 设计出处 | 页面/按钮 | API | 持久化/事件 | CLI | 正向/拒绝用例 | 版本/状态。
必须覆盖所有现有可操作元素和设计中尚无入口的功能，不能只数页面或路由。

规则：
- 加载展示骨架；空集展示“暂无”；接口失败展示错误及重试，不能变为演示数据或假成功。
- 名称、人员、日期、数量、百分比、附件、审批流、使用记录均来自真实记录或明确公式。
- 无权限或业务状态不允许的动作应禁用/隐藏并说明原因；不是借此取消设计要求。
- 后端成功回读后才提示成功；多步操作失败显示真实失败及恢复入口。
- 查询缓存必须区分用户/租户；退出、切换账号/Portal会话后清除旧数据。
- 枚举、文案、视觉色彩、合法静态工具注册表不是 fake；虚构业务值和执行结果才是。
- 契约允许显式demo seed和AI入口占位，但它们不计入生产事实或功能成功。
  生产禁用seed创建/修复/凭据轮换写入口；只在显式隔离范围和专门授权下允许。
- 当前seed修复按同名匹配可能覆盖记录、工具URL及轮换凭据，不能只禁止自动seed。
  修复必须校验可信provenance、seed_key、所属隔离范围及对象版本；不按姓名认领。
  seed/status只读，不返回/轮换密码；人工配置工具URL等字段不得被演示修复覆盖。
- 存量演示记录按可信seed清单预检并标记隔离，保留ID、关联、凭据和原数据。
  不自动删除、不改未知来源记录；无法判断归属的记录列出阻塞，交由用户决定。
  专项验收：同名真实人/项目、人工工具配置、生产账号凭据在seed修复拒绝后完全不变。

六、实现原则与数据安全
----------------------
1. 保留现有JSONB records、users、audit和文件，不为对齐旧表名全量换库。
   先补各领域schema、字段白名单、状态机与关系约束；确有唯一性/历史/任务队列需要时增小表或索引。
   既有数据先检查再加约束，迁移可重入，不删除不认识的字段/记录。
2. 拆 router/records/CLI 的领域代码，公共层只保留注册、存储、鉴权和必要共享规则。
   不引入新微服务、通用工作流引擎、事件总线或复杂仓储抽象。
3. API统一 {items,total,page,page_size} 或明确聚合DTO；分页/排序/筛选在服务器实现。
   日期、小时、枚举、人员归属、URL、文件、动作原因在信任边界校验。
   普通PATCH不得改status/progress/验收/审计等服务端字段，所有动作走共享状态检查。
4. 任务/派发/审批/分工/冲突/待办的关键变化保持事务一致。
   审批最终生效和并发派发需在事务内复检人员有效性、版本、占用和授权。
   新接口有可回读操作ID；重试/重复点击不能新增重复审批、成果、通知或工时。
5. B0前置共享审计契约：tenant、actor、action、object type/id、server time、来源IP、request-id、
   before/after摘要、reason、操作结果；IP只认可信代理链，敏感字段按白名单脱敏，不存口令/票据/token。
   M02维护鉴权及敏感读/拒绝审计；M13负责认证结果/会话；各领域owner负责业务写审计。
   角色/范围/授权、人员绑定、邀请审核、状态变更、配置发布、强制安排、资料版本、导出创建
   必须与对应数据库变更同事务；SA敏感读及导出/下载读审计另记录，不返回隐藏业务内容。
   复用数据库持久化少量通知/导出/清理任务，明确状态、重试和审计；Redis仍用于会话/缓存。
   清理从readyz和GET查询移到明确写操作/受控任务；health/ready只探测依赖，不做业务清理。
6. 本地登录和Portal共存规则、HttpOnly Cookie及CLI Bearer边界统一；不在文档/日志输出凭据。
   权限按“租户 -> 中心/组织 -> 项目/任务 -> 字段/动作”逐层校验，包含导出、历史和源对象撤权。
7. 服务API + 静态页面仍为单服务二进制。CLI可单独编译为服务器验收附件，不另启服务。
   先探测远端测试运行时；必要时在隔离验证目录提供固定版本Bun和源码/依赖快照。
   单测/类型检查在该服务器目录运行，不安装全局Rust/Node，不以本地结果代替验收。
8. 每个非平凡新规则留下最小可运行回归检查，复用现有测试，不只增加mock“路由成功”断言。

八、CLI真实循环、发布及完成标准
------------------------------
所有功能必须有CLI同等能力，包括筛选、详情、状态动作、版本、授权、批量和导出。
扩展现有CLI，不另造一套curl散脚本当产品CLI；补help、参数校验、JSON、退出码及分页。
服务器验收脚本调用产品CLI，创建带唯一前缀的隔离验收数据，不用seed代替真实流程。

每项最少验证：
  合法操作 -> 回读持久化 -> 刷新聚合/关联 -> 审计/通知 -> 业务反向动作
  越权/非法状态/非法输入 -> 预期拒绝 -> 回读确认无副作用
  重复/并发/依赖故障 -> 可恢复结果 -> 无重复、无丢数据、无假成功

三个代表性场景：
1. 任务成果：建组织/人员/项目 -> 标准派发 -> 部门/中心审批 -> 人员确认 -> 分工填报 ->
   上传两版真实文件 -> 成果退回重提 -> 负责人确认 -> 指定验收人验收 -> 归档。
   核对任务/分工/文件版本、工时、负载、inbox、项目统计、审计与归档快照。
2. 冲突：同人同日4h+5h被阻断 -> 全天+1h被阻断 -> 管理者带原因限期强制 ->
   调期后原强制失效 -> 重新协调 -> 到期失效；同时验证待审批预估、隐藏占用及并发发布。
3. 权限：view-only用户直调PATCH/发布/下载 -> 写拒绝且数据不变；撤销项目授权 ->
   旧会话查询任务/甘特/搜索/通知/报表/历史文件一致失权，个人事项不泄露。

发布通道全局只有一个：
  功能worktree提交且干净
    -> fetch并确认origin/HEAD/main、同步干净main
    -> 功能分支rebase最新main并复核
    -> main merge --ff-only
    -> 从main push origin main（不push功能分支，不force）
    -> 干净main make deploy
    -> ssh nexusflow: 类型检查/单测/CLI真实循环/health/version
    -> 失败回功能worktree修复，再完整循环

每次功能交付都及时commit、push、make deploy；不把多个未验收大功能积压到最后一次部署。
上线前备份PG及对象元数据，迁移先预检；发布保存旧二进制与匹配版本记录。
数据库变更尽量增量兼容；不可逆变更或无法判断存量数据时阻塞，不做危险“自动回滚”。
服务version须等于已push提交；部署检查不仅看200，还核对API JSON契约和页面资源身份。

前端验证遵守用户要求：不在本地开环境，不以浏览器自动化作为业务验收手段。
agent提供按钮->API调用链、空/错/无权限状态及真实ID资源证据；用户自行访问页面验收。
CLI可证明业务真实，但不能冒称已验证浏览器点击、像素一致或外部工具执行。

最终FINAL_PASS要求：
- function-coverage每条设计需求都有实现、CLI和服务器证据，不存在无证据“已完成”。
- 生产构建不引用demo业务fixtures，不静默回退、不假动作/假统计，空库和接口失败行为真实。
- 13领域正向链及权限/状态/并发/故障拒绝链通过；历史数据、文件、会话安全。
- 全域CLI循环通过，记录命令、对象ID、预期/实际、提交、时间；敏感值脱敏。
- 没有将HTTP首页兜底、mock测试或健康检查当业务证明。
- 本地main与origin/main一致，功能和修复均已提交，服务器同版本验证通过。
- 已合并且验收的worktree/分支安全清理；删除本轮临时证据/协调文件，关闭本轮创建tab。
  未完成或阻塞的worktree保留；不得关闭既有tab、删除用户文件或遗留未提交修复。
